# Flag-overlap boundary review

Generated by `data/flag_overlap.py` against real `--help` output on this
host (raw data: `data/flag_overlap_report.json`), then classified by hand.
This is the enumerated boundary weir's rule set was missing: every rule
before this pass came from a `FIELD_REPORT_*.md` written after real damage.
This walks the collision space once, up front, instead.

98 single-letter flags exist in both a classic tool and its weir-suggested
replacement. Classification below sorts them into three bins. Only one
collision moved to a new rule (`rg-cap-l-misfire`, added to `rules.go`
2026-09-08) — the bar for "write a rule" is narrower than "flag exists in
both tools and means something different," and the reasons are below.

## Why so few of 98 became rules

A rule is worth writing when a flag collision can cause **silent** wrong
behavior — the command exits 0, looks fine, and did the wrong thing. Most
collisions don't clear that bar, for one of two structural reasons:

1. **The tool is read-only.** `ls`/`eza`, `ps`/`procs`, `diff`/`delta`,
   `df`/`duf`, `cat`/`bat`, `xxd`/`hexyl` only ever produce output — a
   flag mixup gives you a wrong or confusing *display*, never a wrong
   file on disk. 79 of the 98 collisions are in these six pairs. None of
   them got a rule, on the same logic that `weir` doesn't have a rule for
   every cosmetic `ls` vs `eza` flag difference today: wrong output you
   can see and correct is not the failure class this tool exists to catch.
2. **The collision is self-defending.** Where the two tools' flags take
   arguments from different domains (`grep -d {skip,read,recurse}` vs
   `rg -d NUM`), the muscle-memory value fails to parse and the command
   errors loudly instead of silently misbehaving. `grep`/`rg`'s `-d`, `-T`
   are this shape. Not zero risk, but self-correcting the way `rg -r n`
   (below) is not: the whole reason `-r` and `-h` already have rules is
   that grep's own muscle-memory values (`-rn`, `-oh`) happen to be
   *valid* rg argument values too, so rg accepts them and does something
   else entirely, silently.

That leaves the genuinely silent, mutation-relevant cases:

## grep / rg — 32 collisions, the highest-density pair by letter count

| letter | verdict | why |
|---|---|---|
| `-r` | **rule exists** (`rg-r-misfire`, `rg-r-misfire-bundled`) | pre-existing |
| `-h` | **rule exists** (`rg-h-is-help`) | pre-existing |
| `-L` | **rule added** (`rg-cap-l-misfire`, advisory) | grep: files *without* a match (a common "find what's missing X" audit idiom). rg: `--follow` (symlinks). Both are real, unrelated things to want, silent either way — no parse error, no way to tell intent from the command text alone. rg's `--files-without-match` has no short flag at all, so there's no letter-for-letter safe rewrite to auto-apply, which is also why this is advisory and not block: weir's own policy reserves block for rewrites with no semantic risk, and this one has real ambiguity to resolve, not a mechanical substitution. |
| `-d` | reviewed, no rule | `grep -d ACTION` (skip/read/recurse) vs `rg -d NUM` (max-depth) — different domains, rg rejects a non-numeric value, self-defending. |
| `-T` | reviewed, no rule | `grep -T` (tab alignment, rare) vs `rg -T TYPE` (exclude a file type) — requires an argument, obscure enough in practice that a proactive rule isn't worth the table space. Revisit if a real sighting shows up. |
| `-s` | reviewed, no rule | `grep -s` (suppress error messages) vs `rg -s` (`--case-sensitive`) — changes match count, not destructive, no clean single-flag fix to suggest. |
| `-z` | reviewed, no rule | `grep -z` (NUL-delimited lines, the `find -print0` companion) vs `rg -z` (search inside `.gz` files) — real divergence, but only matters when piped into something NUL-aware, and rg's `.gz`-search mode is a no-op on non-`.gz` input rather than corrupting anything. |
| `-E`, `-I`, `-N`, `-U` | reviewed, no rule | different meaning, no destructive path — output-shape or matching-mode changes only. |
| everything else (`-A -B -C -F -H -P -V -a -b -c -e -f -i -l -m -n -o -q -v -w -x`) | same meaning in both | verified against both tools' own descriptions, not assumed |

## sed / sd — 2 collisions

`-f` (sed: script file vs sd: regex flags) and `-n` (sed: `--quiet` vs sd:
`--max-replacements`) both require an argument in both tools and are
unlikely to be hit by muscle memory the way `-r`/`-h` were — sed users
rarely reach for bare `-n` outside a `sed -n 'p'` idiom that doesn't map
onto sd's usage at all. No rule. sd's real landmine (`sd-in-place-write`,
already in the rule set) isn't a flag collision — it's an inverted
default with no `-i` to collide on in the first place, which is exactly
the class of gap this letter-overlap method can't see by construction.

## ps / procs, diff / delta, df / duf, ls / eza, cat / bat, xxd / hexyl — 79 collisions

All six pairs are read-only. Full list is in
`data/flag_overlap_report.json` if a specific one needs a second look, but
none of these clear the silent-and-consequential bar above.

## find / fdfind, awk / mlr — not usable data

`find` on `$PATH` here resolves to GNU findutils when invoked directly
(the way `weir`'s own hooks would run it), which documents almost its
entire surface as multi-character `-name`/`-type`/`-maxdepth` predicates
rather than single-letter flags — the near-zero overlap this script found
is a real property of find's grammar, not a scraping failure. `awk`/`mlr`:
`mlr`'s help system is verb-subcommand-based (`mlr help topics`, not a
flat `--help` flag dump), and this script's help-scraping didn't reach a
usable page. Both would need a different extraction approach than
`--help`-diffing to say anything real; not attempted here.
